# Sign-in latency follow-up — 2026-10-22

The learner supplied a sign-in screenshot showing the form waiting for the account service. Live browser probes to both /api/v1/health on the website and /v1/health on the API showed Render's Application loading interstitial. A separate Node public-health probe timed out at 70 seconds. These observations identify an upstream availability/wake-up wait, not slow password typing or evidence of lost progress. Official Render documentation confirms free instances sleep after 15 idle minutes and usually need about a minute to wake: https://render.com/docs/free . No always-on guarantee is claimed, and no paid compute, keep-alive cron, account migration or credential changes were made.

There was also avoidable database work. getAccount deleted expired sessions before every read even though its SELECT already enforces expires_at > now(). That cleanup is now performed during session creation, not on every read. createSession combines the existing expired-session cleanup and the new session INSERT into one PostgreSQL data-modifying CTE. Session lookup and creation each use one database round trip instead of two. The cryptographic hash, cookie settings, password verification, expiration predicate, rate limits, account IDs and progress are unchanged. This improves the application path but does not bypass the hosting wake-up.

Synthetic tests first reproduced both two-query paths, then verified the single-query paths, hashed-token lookup, missing/expired rejection and failure without a cookie. Full suite: 206 tests passed. No real user password or microphone was used for tests. AI assistance was used for implementation and verification.

The previous release build was blocked by the Next.js 16.4.0 security warning. This run pins the verified patch 16.4.1, following https://github.com/vercel/next.js/security/advisories/GHSA-2464-fhr4-w9xw . The dependency diff is confined to Next and its version-matched packages; npm reported zero vulnerabilities after install. No unrelated model or provider update was made. The previously tested 8-MiB generated-audio cache fix is included in this release as well. Production build/deployment evidence follows when complete.
